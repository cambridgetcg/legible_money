## Insights Discovered

### DevNet Insights

1. **Chain-ID mismatch trap**: The `cosmos-devnet.sh` script displayed `legible-devnet-1` in its banner but the actual genesis chain-id is `lgm-devnet-1`. Tx signing with wrong chain-id gives cryptic "signature verification failed" error (code 4). Always verify chain-id from genesis, not script output.

2. **Stale state on restart**: Running `cosmos-devnet.sh start` on a node that was previously initialized regenerates keys (new addresses) but doesn't clear old chain state. Result: new keys can't find their accounts on the old chain. **Must reset before fresh start** (`cosmos-devnet.sh reset && cosmos-devnet.sh start`).

3. **Minimum gas price enforcement**: The devnet starts with `--minimum-gas-prices 0.025ulgm`. A tx with `--fees 500ulgm` and `--gas 200000` fails because 500/200000 = 0.0025 < 0.025 minimum. Must use `--gas-prices 0.025ulgm` with auto gas, or calculate: `fees >= gas * min_gas_price`.

4. **REST API 501**: The REST LCD endpoint returns 501 for some custom module queries. This is expected for hand-written service descriptors that lack proto-generated gateway bindings. SDK standard modules (bank, staking, mint) work fine.

5. **gRPC registration warnings**: ~30 warnings at startup about "skipped gRPC service registration (proto types not generated)". These are cosmetic — hand-written types don't have proto registrations. Won't affect functionality until proto codegen is complete.

### CI/CD Process Insights

6. **Go chain was invisible to CI**: The existing `ci.yml` only ran TypeScript checks. The Go chain (11.5K LOC, 27 test packages, 200+ files) had zero CI coverage. Any Go regression would be caught only by local `make pr-check`. This is the #1 finding — dual-stack projects need dual-stack CI from day one.

7. **Agent tier validation is label-driven**: Without an on-chain agent registry, the agent-ci workflow uses PR labels (`agent-tier-0` through `agent-tier-3`) as a trust-but-verify mechanism. This works for the private repo phase but needs upgrading to chain-verified tiers before public launch.

8. **Metrics collection bootstraps the adaptive loop**: Even without the x/autopoiesis module, collecting CI metrics as JSON artifacts creates a queryable history. When Phase 3 (metrics→chain) ships, the historical data can be backfilled.

9. **Pre-existing test failures are CI poison**: The `TestExpireStaleEvidence` failure was pre-existing and silent (only caught by `make go-test`, not CI). Any session running `make pr-check` would see it and might assume their changes caused it. CI should establish a known-good baseline and alert on regressions, not just failures.

### Open-Source Dev Flow Insights

10. **Stash-and-branch works but is fragile**: Stashing uncommitted changes, creating a branch, and popping the stash preserves work but the Makefile got temporarily reverted by the stash. Better flow: commit work-in-progress to a new branch first, then continue.

11. **Feature branch scope discipline**: This session touched CI config, Makefile, a test bug fix, a health check script, and a session log. That's borderline for one PR. The open-source flow recommends <500 LOC non-test — this PR is within bounds but tests the upper limit.

12. **Session logs as branch artifacts**: Writing `.claude/sessions/2026-02-15-cicd-flow.md` on the branch serves dual purpose: (a) context for continuation sessions, (b) merge to main provides historical record. This pattern validates the open-source flow design.
